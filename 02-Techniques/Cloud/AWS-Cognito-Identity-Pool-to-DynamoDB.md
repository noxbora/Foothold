# Cognito Unauthenticated Identity Pool to DynamoDB Dump

Target pattern: a static, login-free web app hosted on [[Security-Terms#^s3|S3]] that still shows per-user data. The app obtains real AWS credentials in the browser from a Cognito Identity Pool configured to allow unauthenticated identities. The vulnerability is not Cognito itself — it is the [[Security-Terms#^iam|IAM]] policy on the unauth role being scoped too broadly (table-wide read instead of own-record read). The chain below turns "any anonymous visitor" into "every user's record".

## Confirm the app ships logic to the browser

**Why now** — you have an S3 website URL and it looks blank or static. Before assuming a dead end you check the defining fact of an S3-hosted app: a static host runs no server-side code, so any personalization *must* be shipped to the client, which means the credential machinery is in the page and readable.

```bash
curl -s http://<bucket>.s3-website-<region>.amazonaws.com/
```

- `-s` → silent: drop the progress meter so the HTML is the only output.
- the endpoint hostname → it hands you two things for free: the **region** (`s3-website-us-east-1`) and often the 12-digit **AWS account ID** embedded in the bucket name (`app-<account-id>`). Record both.

**What you will see**

- **Found** — HTML that references one or more `.js` bundles (`<script src="app.js">`). The bundle path is the thread to pull; the logic lives there, not in the HTML.
- **Empty** — a genuinely blank page with no script tags is rare and would mean the app is not client-side after all. Far more often "blank" means the HTML is a shell and the content is rendered by JS — so an empty-looking body is a reason to read the bundle, not to leave.
- **Error** — `NoSuchBucket` / `AccessDenied` XML means the bucket name or region is wrong; a connection timeout means the website endpoint is not enabled and you have the REST endpoint instead. Fix the hostname before concluding anything.
- **Noise** — analytics and framework bundles (`react`, `gtag`) are not the app; the file with a name like `app.js`, `main.js` or `bundle.js` is the one that carries the AWS config.

**Then** — a referenced bundle goes to the next section. Record the region and account ID now; you use the region as a grep anchor immediately and the account ID later to confirm the credentials you mint belong to the target's account.

## Pull the AWS config out of the bundle

**Why now** — you have the app's JS bundle and you want the credential-issuing configuration without reading minified code line by line. Any AWS [[Security-Terms#^sdk|SDK]] client keeps its region, pool ID and table name together in one config block, so one grep on the region string lands you in the middle of everything you need.

```bash
curl -s http://<target>/app.js | grep -iE "us-east-1|identitypool|region|tablename|apigateway|cognito"
```

- `grep -iE` → case-insensitive extended regex; anchor on the **region string** first because in an SDK config the region sits beside the pool ID and table name, so a hit drags the rest into view within a few lines.

Values worth extracting: `IdentityPoolId` (format `<region>:<uuid>`), `AWS_REGION`, `TABLE_NAME`, and any `UserPoolId`, API Gateway base URL, or S3 bucket name.

**What you will see**

- **Found** — a config object with `IdentityPoolId: 'us-east-1:<uuid>'` and a `TABLE_NAME`. The SDK operation the app calls tells you the *intended* scope: `dynamodb.getItem` with a single `Key` means the app means to read **one** record — so anything broader that succeeds later is the misconfiguration, spelled out.
- **Empty** — no matches means the config is in a different bundle or loaded from a separate JSON; grep the other `.js` files the page pulled, and any `/config.json` it fetches.
- **Error** — a minified single-line bundle can bury the value with no newline for `grep` to cut on; pipe through `js-beautify` or just widen with `grep -o '.\{0,80\}identitypool.\{0,80\}'`.
- **Noise** — a client-side `localStorage` identifier generated by `Math.random()` (e.g. `guestId`) looks like an access boundary and is **not** one: it is an attacker-supplied lookup key. The IAM policy is the only thing that could enforce separation, which is exactly what you test next.

**Then** — an `IdentityPoolId` goes straight to the credential-minting step. The `TABLE_NAME` and the observed `getItem` scope are what you hold up against the role's real permissions later; the gap between them is the finding.

## Mint anonymous AWS credentials

**Why now** — you have an `IdentityPoolId` and the pool is configured for unauthenticated identities, which means it will hand real AWS keys to *any* caller, not just a browser. You run the two-step issue chain to become an authenticated-to-AWS principal you can point at any service.

```bash
aws cognito-identity get-id --identity-pool-id <region>:<uuid> --region <region> --output json
```

```bash
aws cognito-identity get-credentials-for-identity --identity-id <region>:<uuid> --region <region> --output json
```

- no credentials and no `--no-sign-request` → both calls are unauthenticated **by design**; that is the whole vulnerability, so do not add auth.
- `get-id` returns an `IdentityId`; feed it to `get-credentials-for-identity`, which returns `AccessKeyId`, `SecretKey`, `SessionToken`, `Expiration`.
- `--output json` → include it explicitly; a broken CLI default is the first gotcha below.

**What you will see**

- **Found** — an `AccessKeyId` beginning **`ASIA`** (not `AKIA`), plus a `SecretKey`, a `SessionToken`, and an `Expiration`. `ASIA` marks temporary [[Security-Terms#^sts|STS]] credentials: the `SessionToken` is mandatory on every later call and the keys die at `Expiration`.
- **Empty** — no blank state: the pair returns credentials or an error. An empty-looking `{}` usually means you read the wrong field — the keys are nested under `Credentials`.
- **Error** — `NotAuthorizedException: Unauthenticated access is not supported` means the pool does **not** allow anonymous identities — the chain is closed and you look for an authenticated path instead. `ResourceNotFoundException` means a wrong `IdentityPoolId`.
- **Noise** — an `IdentityId` on its own is not a credential; it is only the ticket you exchange in the second call. Do not try to use it as a key.

**Then** — with keys in hand, load and confirm the identity in the next section. `Unauthenticated access is not supported` sends you back to look for a login the app does use.

## Load the keys and confirm who you are

**Why now** — you have `ASIA` keys and need them active in your shell, and you want to know exactly which role you are assuming before spending calls, because the role name tells you the boundary you are testing.

```bash
export AWS_ACCESS_KEY_ID="ASIA..."
```

```bash
export AWS_SECRET_ACCESS_KEY="..."
```

```bash
export AWS_SESSION_TOKEN="..."
```

```bash
aws sts get-caller-identity
```

- all three `export`s → environment variables take precedence over `~/.aws/credentials`, so this leaves any existing profile untouched. **`AWS_SESSION_TOKEN` is not optional** for `ASIA` keys; omit it and every call fails signature validation with a confusing `InvalidClientTokenId`.
- `get-caller-identity` → costs nothing, needs no permission, and confirms the keys work before you build on them.

**What you will see**

- **Found** — an `Arn` like `arn:aws:sts::<account>:assumed-role/<app>-cognito-unauth-role/...`. The role name containing `unauth` confirms you are operating as an anonymous visitor **inside the target's account**; the account number should match the one from the bucket name.
- **Empty** — no blank state: `get-caller-identity` always answers with an `Arn` or an error. A blank return means the CLI swallowed output — see the `--output None` error below.
- **Error** — three environment gotchas cost real time and are not vulnerabilities: `Unknown output type: None` means the CLI config has `output = None` — fix with `--output json` per call or in `~/.aws/config`. `Could not connect to the endpoint URL: "https://sts.None.amazonaws.com/"` is the same fault on the region — `export AWS_DEFAULT_REGION=us-east-1`. `ParamValidation: ... required: --identity-pool-id` after pasting a multi-line command onto one line means a trailing `\` line-continuation survived — remove all backslashes when collapsing to one line.
- **Noise** — an `Arn` naming an *authenticated* role, or a different account number, means these keys are not the anonymous target role; re-check the pool ID.

**Then** — a confirmed unauth role goes to the permission-mapping step: the whole game now is finding where its real permissions exceed the app's intended `getItem`.

## Map what the role can actually reach

**Why now** — you are the unauth role and the app only ever called `getItem` on one record. The misconfiguration, if it exists, is in the IAM policy, not the app — so you probe the role's *real* permission surface rather than assuming it matches the app's behaviour. There is no vertical escalation here; the escalation is lateral, from "my record" to "every record".

```bash
aws dynamodb list-tables --region <region>
```

```bash
aws dynamodb describe-table --table-name <table> --region <region>
```

```bash
aws iam get-role --role-name <role>
```

```bash
aws iam list-role-policies --role-name <role>
```

```bash
aws s3 ls
```

```bash
aws lambda list-functions
```

```bash
aws secretsmanager list-secrets
```

- `list-tables` → does the role see tables beyond the one hardcoded in the JS? Broader visibility than the app uses is the first sign of over-scoping.
- the `iam` calls → usually denied for an unauth role, but always worth one call: a role that can read its own policy tells you exactly where the boundary is.
- the `s3`/`lambda`/`secretsmanager` line → quick breadth checks for other services the same over-scoped policy may cover.

**What you will see**

- **Found** — `list-tables` returning the target table (or more), and `describe-table` returning its key schema. That the call **succeeds at all** as an anonymous role is the lead; the schema tells you the partition key you would need for a legitimate `getItem`.
- **Empty** — `list-tables` returning `{"TableNames": []}` while the app clearly reads a table means the policy grants item access without list access — not a dead end. Go straight to `scan` on the known `TABLE_NAME`; you do not need `list-tables` to succeed.
- **Error** — `AccessDeniedException: ... is not authorized to perform: dynamodb:ListTables` is a precise map of the boundary, not a wall: read *which* action and resource it names. A role denied `ListTables` is very often still allowed `Scan` on the specific table.
- **Noise** — the `iam` and `secretsmanager` calls denying is the expected, boring case and says nothing bad; do not read a denial there as the whole role being safe.

**Then** — read the **Action/Resource mismatch** as the finding: the app performs `GetItem` on one item, so the policy should be scoped to `GetItem` with a condition tying the key to the caller's `cognito-identity.amazonaws.com:sub`. A policy granting `dynamodb:*` or `dynamodb:Scan` on `Resource: *` is the defect — cash it in with the dump below.

## Dump the table

**Why now** — the role can reach the table more broadly than the app ever intended, and `Scan` is `getItem`'s table-wide counterpart: it reads every item with no key and no filter. A successful scan is the proof of the misconfiguration and the loot in one call.

```bash
aws dynamodb scan --table-name <table> --region <region> --output json > scan.json
```

- `> scan.json` → redirect rather than page; a large scan opens in a pager where `:` means more output follows and it is easy to think the command hung. A file is also your evidence.
- `Scan` reads **every** item before any filter is applied, so it both proves the finding and consumes read capacity regardless of what you keep.

Flatten DynamoDB's typed attributes into readable lines, and filter server-side only if the table is too large to eyeball:

```bash
jq -r '.Items[] | .guest_id.S + " | " + .name.S + " | " + .notes.S' scan.json
```

**What you will see**

- **Found** — a `Count` / `ScannedCount` in the response tail **greater than one**, and items belonging to other users. `Count > 1` is the proof: an anonymous caller read records that are not theirs. Flags and secrets typically sit in free-text fields like `notes` or `password`.
- **Empty** — `Count: 0` on a table the app clearly uses means either a wrong `--table-name` or a region mismatch; re-check both against the bundle. It does not mean the table is empty.
- **Error** — `AccessDeniedException` on `Scan` means this specific action is *not* in the over-scoped policy after all — the role may still allow `GetItem`, so the horizontal read is closed but a targeted read of known keys may not be. `ValidationException` usually means a malformed `--filter-expression`.
- **Noise** — your **own** client-generated `guest-<random>` ID will usually be absent from the results: it only ever lived in `localStorage`, never persisted server-side. Its absence is expected, not an error.

**Then** — a table dumped with `Count > 1` is the finding; write it up (below). Redirect large scans to a file and triage with `jq`; when even that is too much, filter server-side:

```bash
aws dynamodb scan --table-name <table> --region <region> --filter-expression "contains(notes, :f)" --expression-attribute-values '{":f":{"S":"FLAG{"}}'
```

## Reportable findings from this pattern

1. Cognito Identity Pool permits unauthenticated identities and issues live AWS credentials to any anonymous caller.
2. The unauth IAM role grants `dynamodb:Scan` over the whole table, letting any visitor read every other user's record — a horizontal authorization failure (IDOR at the IAM layer).
3. Passwords stored in plaintext in the `password` attribute. Independent finding; critical on its own.
4. [[Security-Terms#^pii|PII]] exposed at scale: email addresses, phone numbers, and precise `location` coordinates for all users.
5. Authorization enforced by a client-generated `localStorage` identifier — attacker-controlled, therefore no control at all.

## Remediation notes

Scope the unauth role to `dynamodb:GetItem` on the specific table, with an IAM condition binding the partition key to `${cognito-identity.amazonaws.com:sub}` so each identity can only read its own item. Remove `Scan` entirely. Disable unauthenticated access on the pool if the app can require sign-in. Hash passwords; never store credentials as a table attribute. Move any query the client cannot be trusted to build behind an authenticated API layer.

## Reading the output

Two tells run through the whole chain. An `AccessKeyId` beginning `ASIA` rather than `AKIA` is a temporary STS credential — the `SessionToken` is mandatory on every call and the keys expire, so a chain that worked an hour ago failing with a signature error usually just means they lapsed; re-mint them. And a `Scan` returning `Count` greater than one is the entire finding in one number: it is the proof that an anonymous role read data that was never scoped to it.
