# 2049 — NFS

A file server that hands out directories over the network and trusts the client to say who it is. There is no password: the client sends a numeric user id, and the server applies that user's permissions. Whoever controls the client controls the identity, which is what makes this service worth the visit.

Reach for this note when `2049` is open. The escalation that follows from a badly written export lives in [[NFS-No-Root-Squash]]; this note is the part before it, when you are still outside.

## 1 — What is running, and what is exported

**Why now** — you have an open port and nothing else. The service is a family of programs registered with a portmapper, and asking the portmapper is both cheaper and more honest than probing each one.

```bash
rpcinfo -p TARGET
```

- The reply lists every registered program with its version and port. It tells you which protocol versions are on offer, and that single fact changes everything below: version 3 lists its exports to anyone, version 4 does not.
- `111` is the portmapper itself. It is frequently open when `2049` is filtered, and it still answers, so a closed `2049` in your scan is not the end of the question.
- Note the highest version number beside the file-server entry before running anything else.

**What you will see**

- **Found** — entries naming the mount and file-server programs, with versions. Versions `2` and `3` mean the export list is readable; version `4` only means the service is there.
- **Empty** — no reply at all usually means `111` is filtered rather than absent, since a running file server has to register somewhere.
- **Error** — `Program not registered` means the portmapper answered and the file server is not behind it, which happens on version-4-only hosts by design.
- **Noise** — the list includes the portmapper's own entries in several versions and protocols. They are stock.

**Then** — version 3 present goes to the export list and then section 2. Version 4 only goes to the Rarely section, because there is no list to ask for.

## 2 — Mounting it, and being the right person

**Why now** — you know an export exists. Mounting is read-only reconnaissance until you look at who owns the files, and the ownership is the finding.

```bash
sudo mount -t nfs -o ro,vers=3 TARGET:/srv/share /mnt/target
```

```bash
ls -lan /mnt/target
```

- Mount read-only first. A writable mount invites a mistake on someone else's filesystem, and nothing in this section needs write access.
- `-o vers=3` is worth stating explicitly. A client that negotiates version 4 against an export written for version 3 fails with a message about the path, which reads like the export name is wrong when it is not.
- `ls -lan` is the load-bearing command, and `n` is why: it prints numeric owner ids instead of translating them into your machine's names. Your `alice` and their `alice` are different people; the number is the only thing both sides agree on.
- A file you cannot read is owned by a numeric id you are not. Create a local user with that exact id, become them, and the server will hand the file over, because the id is the whole of the authentication.

**What you will see**

- **Found** — files owned by ids that are not yours, especially in home directories: keys under `.ssh`, configuration files, database dumps, backups.
- **Empty** — a mount that succeeds and shows an empty directory is a genuine answer about that export. Check the other exports before concluding the host is bare.
- **Error** — `access denied by server` means the export is restricted by client address, and your address is not on it. `No such file or directory` after a clean mount usually means the version mismatch above, not a wrong path.
- **Noise** — `nobody` or `65534` as the owner means the server squashed the identity, which is the safe configuration working as designed. That is not a finding, it is the absence of one.

**Then** — a private key goes to [[22-SSH]]. Configuration files and dumps go to [[Config-File-Looting]]. A writable export owned by root goes to [[NFS-No-Root-Squash]], which is where this stops being reconnaissance.

## Rarely — worth one command, not worth a step

**Why now** — the portmapper says version 4 only, or the export list came back empty while the port is clearly open.

```bash
sudo mount -t nfs4 TARGET:/ /mnt/target
```

```bash
nmap -p111,2049 --script nfs-showmount TARGET
```

- Version 4 has a single root that gathers the exports beneath it, so mounting `/` and listing it is the replacement for asking for a list. There is no discovery step because the protocol removed one.
- The `nmap` script does the same job as the export listing and is worth one run when the client tools are missing from the box you are on.
- If the mount succeeds and shows nothing, the export is restricted to specific client addresses and no amount of client-side work changes that.

**What you will see**

- **Found** — a directory tree under the mount point that the export list never advertised.
- **Empty** — the normal answer on a restricted server. These are lottery tickets, not steps.
- **Error** — a hanging mount that never returns is the filtered case; interrupt it rather than waiting.
- **Noise** — an empty mount point looks identical to a successful mount of an empty share. Confirm with the mount table before deciding which one you have.

**Then** — anything readable goes back to section 2 and the numeric ownership question. Nothing readable means the export is address-restricted and the next port is a better hour.

## Reading the output

Everything on this service comes down to one idea: the server is not authenticating a person, it is believing a number. So the important column in any listing here is the owner id, and the important question is whether you can become it.

The second thing worth holding is that a squashed identity is a working defence, not a broken command. `nobody` in the owner column means the administrator configured this correctly, and reading it as a failure of your mount wastes the evening.
